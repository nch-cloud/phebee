# Code issues parked during the Supplementary Methods audit

These code issues turned up on 2026-10-02 while the Supplementary Methods for
the JAMIA Open revision were audited against v1.0.3-rc7 (commit `1345205`).
None of them changes a manuscript number. The manuscript text was changed to
describe the code as it behaves, so fixing any of these may mean a matching
text change. None has been fixed yet. The decision still to make is which ones
go into v1.0.3.

Line numbers refer to `1345205`.

## Correctness

### 1. View refresh double-counts when a run is applied twice

`scripts/materialize_project_subject_terms_emr.py:221` and `:303` merge with
`evidence_count = target.evidence_count + source.evidence_count`. The refresh
reads every evidence row carrying the run identifier, not only the rows the
current attempt appended. Re-running an import whose refresh already finished
therefore doubles that run's counts in both views. Today the only repair is a
full rebuild.

**Manuscript:** "Recovery by re-execution" says view refresh "is not
idempotent", and "Reconciliation" says re-applying a run "would double them".

### 2. The one-day lookback is hardcoded in the import state machine

`statemachine/bulk_evidence_import.asl.json:281` passes the literal
`'--lookback-days', '1'`. The script's own default is 1000. Re-running an
import more than about a day after the original finds no evidence for the run
(`created_date` keeps its original value, because the append is insert-only),
and the refresh step exits 1. The value can't be overridden from the execution
input.

**Possible fix:** read it from the input, keeping 1 as the default.

**Manuscript:** "Recovery by re-execution" and partial-failure item (i) both say
"within a day of its execution, or after that window by a full rebuild". With
a configurable lookback, they could say "within the configured lookback window".

### 3. Re-running under a new run identifier reports success but repairs nothing

With a new `run_id`, the append writes nothing. TTL generation finds no rows
for that ID and returns early. `CheckSubjectLoadsExist`
(`bulk_evidence_import.asl.json:228-235`) then defaults to `NotifySuccess`, so
materialization is skipped and the run reports success. `run_id` is supplied by
the caller (`validate_bulk_import.py`), so it's easy to do this by mistake.

**Possible fix:** fail, or at least warn, when a run appends nothing and
produces no loads.

### 4. Bulk import watches only the first Neptune load, and can loop forever

`bulk_evidence_import.asl.json:181` and `:244` poll only `loads[0].load_id`.
The status choices (`:192-199`, `:255-262`) handle only `LOAD_COMPLETED` and
`LOAD_FAILED`. Any other terminal status, such as `LOAD_CANCELLED`, falls
through to the wait state and polls until the execution times out.

### 5. `remove_evidence` can't repair a failed graph deletion

`functions/remove_evidence.py:26-33` returns 404 "Evidence not found" when the
row has already gone. If the evidence row was deleted but the TermLink deletion
failed (partial-failure state iv), re-issuing the removal never reaches the
graph step. Rebuilding only the graph doesn't fix it either, because the graph
is regenerated from the by-subject view. The only working repair is to rebuild
the views and the graph together.

**Manuscript:** item (iv) says "repaired by rebuilding the views and graph
together".

### 6. Mondo descendant expansion can use the HPO version

`functions/get_subjects_pheno.py:51-68` picks a single `term_source_version`
from the request's `term_source`, which defaults to `hpo`.
`layers/phebee-utils/phebee/utils/iceberg.py:1746-1749` applies that one
version to every source in the term filter. A Mondo term with
`include_child_terms` is then expanded against the HPO release identifier. That
finds no Mondo hierarchy rows, so the descendants are silently dropped. The
version should be resolved per source whenever one isn't given explicitly.

### 7. Exported Phenopacket labels are CURIEs

`iceberg.py:1954` falls back to `term_id` when `term_label` is missing.
`term_label` is always NULL in the views
(`materialize_project_subject_terms_emr.py:186`, `:270`), so every exported
feature's `label` holds the CURIE.

**Manuscript:** "Import and export validation" now says this.

## Security

### 8. SQL and SPARQL are built by string interpolation

Request values are formatted directly into Athena SQL and SPARQL, for example
`iceberg.py:2002`, `:2030` and `layers/phebee-utils/phebee/utils/sparql.py:247`.
Every caller is already IAM-authorized, but any authorized caller could still
inject into a query. Values should be parameterized, or at least validated as
IRIs or CURIEs.

### 9. The read-only SPARQL graph check skips the default graph

`functions/execute_sparql_readonly.py:146-158` checks only IRIs named in
`GRAPH <…>` or `FROM <…>`. A query that names no graph isn't checked at all.
If Neptune's default graph is the union of the named graphs, such a query can
read project graphs, which the function is meant to block because they may
contain PHI. The function has no API route, so only a principal allowed to
invoke it directly can do this.

### 10. An unused StartSyncExecution grant

`template.yaml:266-270`, in `PheBeeAPIPolicy`, grants `states:StartSyncExecution`
on `ImportPhenopacketsSFN`, which nothing calls synchronously. Remove it.

### 11. Creator identity is whatever the caller declares

The evidence creator fields come from the request body and aren't checked
against the SigV4 principal.

**Manuscript:** "Auditability" says "as declared by the caller, not derived
from the authenticated principal". Deriving the identity, or at least
recording the principal ARN as well, would strengthen the audit trail.

## Operations

### 12. Iceberg snapshots are never expired

No `expire_snapshots`, VACUUM or retention property exists anywhere in the
repo. Deleted evidence rows can still be recovered from earlier snapshots by
time travel, and storage grows without limit.

**Manuscript:** "Deletion semantics" says expiry "currently is not scheduled
within PheBee".

### 13. The deletion Lambda outlives the API timeout

The removal functions can run for up to 90 s, but API Gateway's integration
timeout is about 29 s. A slow cascade returns 504 to the client while it keeps
running. The client can't tell this from a failure.

## Tests

### 14. The ontology updater tests check less than the hierarchy needs

- `tests/integration/test_update_hpo_sfn.py:171` and
  `test_update_mondo_sfn.py:208` require only `ontology_source, term_id,
  term_label, depth`. They omit `version` and `ancestor_term_ids`, the two
  columns descendant expansion filters on.
- The term-count tests (`test_update_hpo_sfn.py:131`) count across all
  installed releases.
- The Mondo root-term test (`test_update_mondo_sfn.py:232-240`) has no version
  filter. It would fail once two Mondo releases are installed.

**Manuscript:** "Ontology version handling" was softened to match these tests.
Its wording could be strengthened again after a fix.

## Found in the final audit (2026-10-04)

### 15. A rebuild reloads the newest upstream ontology release

`statemachine/rebuild_materialized_data.asl.json:326-354` starts the HPO,
Mondo and ECO updaters with `{"test": true}`. `functions/download_github_release.py:31-35`
always fetches the newest GitHub release, and `test` only skips the cache
check. A rebuild therefore installs whatever is newest at rebuild time, not
the releases that were installed before it, and earlier releases aren't
reloaded into the graph.

**Manuscript:** "Reconciliation against the system of record" says the graph
is reloaded "together with the installed ontologies".

### 16. Subject and project removal delete the mapping first and can orphan evidence

- `functions/remove_subject.py:74-89` deletes the DynamoDB mappings before
  anything else. If the evidence cascade then fails (`:110-118`), the failure
  is logged and 200 is returned.
- `functions/remove_project.py:138-140` deletes each subject's mappings
  before its evidence deletion. A later failure (`:189`) fails the request,
  but the mappings are already gone.
- Either way, a subject can be left with evidence but no mapping. A retry
  can't find it. A full rebuild doesn't remove it, because
  `scripts/rebuild/materialize_all_analytical_tables.py:127` builds the
  by-subject view from the whole evidence table, and validation passes
  because its baseline is the evidence table.
- If the remaining-mappings query fails (`remove_subject.py:103-105`), the
  subject is treated as still mapped, and its evidence is kept.

**Manuscript:** "Deletion semantics" ("ordered evidence first"), and
"Propagation and partial-failure states" ("Four partial-failure states",
"evidence store is updated first").

### 17. Project removal: more steps are best-effort than the text says

- The final project-wide `DELETE FROM by_project_term` is only logged on
  failure (`remove_project.py:243-257`).
- A failure of the step-1 DynamoDB query is logged and the removal continues
  (`:112-114`).
- That query isn't paginated (`:93-96`).

### 18. Workload 4/5 term pool comes from the first batch file only

`tests/integration/performance/test_evaluation_perf_scale.py:889-903`: at
5k and above, the pool is the 4,297 distinct terms in the first 10,000
records, not all 7,000. Not a bug, but the manuscript describes it as
"distinct terms in the dataset".

### 19. Generated records carry `term_source.version = "unknown"`

`tests/integration/performance/conftest.py:424-437` looks for metadata keys
`release`/`version`. The term JSON has `hpo_data_version`, so every
benchmark record has `"version": "unknown"`. The fallback is
`PHEBEE_EVAL_HPO_VERSION`.

## Found in the main-text audit (2026-10-04)

### 20. Bulk ingestion drops qualifier types other than the three standard ones

`scripts/bulk_evidence_processor.py:282-339` hashes only `negated`, `family`
and `hypothetical`, and `:733-747` stores only those three. Any other key in
`contexts` is silently dropped. `extract_evidence_records` (`:480-483`) would
keep them, but nothing calls it. `/evidence/create` does keep arbitrary types
(`functions/create_evidence.py:84-104`).

**Manuscript:** "Qualifiers and uniqueness" says the model "accepts and
persists additional qualifier types provided by upstream extraction or
curation tools".

### 21. The R6 re-ingest test can't detect evidence duplication, or the absence of a graph load

`tests/integration/evaluation/test_evaluation_end_to_end.py:823-864`
re-ingests under a new `run_id`. It asserts one TermLink with an unchanged IRI
and never counts evidence rows. Because of #3, the second run appends nothing,
generates no Turtle and loads nothing. The test therefore passes whether or not
graph loading is idempotent.

**Manuscript:** reviewer 1 comment 4 asks for evidence-level idempotency to be
demonstrated. The Results claim only "did not create duplicate TermLinks".

## Found in the rc7 integration run (2026-10-05)

### 22. A full rebuild fails once more than about 63 projects exist

`functions/start_neptune_bulk_load.py:65-122` starts one Neptune bulk load per
graph, meaning the subjects graph plus one per project, all with
`queueRequest: TRUE`. Neptune holds at most 64 queued loads. In the
2026-10-05 run, dev held 98 project graphs, most of them left behind by
earlier tests. The load after the 64th failed with "Max load task queue size
limit breached. Limit is 64".

The exception becomes a `statusCode: 500` payload, and the Lambda task still
succeeds. `CheckSubjectLoadsExist`
(`statemachine/rebuild_materialized_data.asl.json:438-446`) then reads
`$.loadStart.Payload.body.total_loads`, which isn't there, and the execution
fails with `States.Runtime`. The loads already queued keep running, and
nothing watches them.

**Possible fix:** submit loads in waves of no more than 64 (or keep a sliding
window). Have the state machine check `statusCode`, or make the Lambda raise,
so the failure is reported as such. This is related to #4.

**Manuscript:** "Reconciliation against the system of record" presents the
rebuild as the recovery path. At institutional scale it holds only while the
project count stays under the queue limit.

**Test:** `test_rebuild_state_machine.py::test_full_rebuild` failed on this
(execution c92ca163). It runs against everything in the stack, so it depends
on how many projects earlier tests left behind.

**Preferred fix (first raised 2026-09-22):** write N-Quads, with each
statement's named graph inside the file, instead of per-project Turtle.
Loads are split per project only to set `namedGraphUri`, so one load could
then cover every graph. That removes the queue limit and makes a rebuild
faster. It changes both generators
(`scripts/rebuild/generate_all_ttl_from_analytical.py`,
`functions/generate_ttl_from_iceberg.py`, despite its "N-Quads" docstring),
the load `format`, and the status checking. Batching loads to 64 or fewer is
the smaller fallback. Also latent: the `list_objects_v2` calls in
`start_neptune_bulk_load.py` aren't paginated, which caps a load at 1,000
project prefixes.

**Decision (2026-10-06):** moved to the backlog and kept out of v1.0.3. The
deployment is far from 63 projects. Until it's fixed, a full suite run has to
reset the stack first, or run `test_rebuild_state_machine.py` on its own.

### 23. create_evidence can time out on a stalled Athena read, and the test helper hides it

In `test_get_subjects_pheno.py::test_get_subjects_pagination_basic`
(2026-10-05 19:41), one of four parallel `CreateEvidenceFunction` invocations
behaved as follows:
- the evidence row and the TermLink were written;
- the function then waited on the Athena read of `subject_terms_by_subject`
  from 19:41:27 until the 90 s Lambda timeout;
- the view update never happened. This is partial-failure state (ii).

A concurrent invocation hit `ICEBERG_COMMIT_ERROR` on the view update, which
was logged and handled.

The timed-out invocation returned a Lambda error payload with no
`statusCode`. `tests/integration/conftest.py:629` indexes
`result["statusCode"]`, so the failure appears as `KeyError`. The helper
should check `FunctionError` and print the payload.

**Possible fix:** bound the Athena wait in the per-evidence view update below
the Lambda timeout, and fail cleanly with a retryable error. This is related
to #13 (90 s Lambda vs the API timeout).

## Found in the full_vpc integration run (2026-11-12)

### 24. TLS certificate verification is disabled for Neptune

`layers/phebee-utils/phebee/utils/neptune.py:214` and `:222` call
`requests.get/post(..., verify=False)` against the Neptune SPARQL and loader
endpoints, and every Neptune-facing Lambda logs an `InsecureRequestWarning`.
Traffic stays inside the VPC, but a compliance reviewer will flag it, and it
defeats the point of IAM-signed requests if the peer is not authenticated.
Neptune presents an Amazon-issued certificate that the default `certifi`
bundle trusts, so `verify=True` is expected to just work.

**Possible fix:** drop `verify=False`, run the Neptune integration tests, and
only if a hostname mismatch appears, pass the cluster endpoint's CA bundle
explicitly.

Also seen in this run: #22 (rebuild with more than 63 projects) reproduced
exactly, with 69 queued loads after a three-hour suite run left 69 test
projects behind.
